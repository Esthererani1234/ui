# Launch readiness — 22 October 2026

Status: **not yet cleared for public launch**. This is an incremental hardening release, not a certification of security or legal compliance.

## Implemented

- Custom password recovery requires a matching verified phone and a recovery-specific SMS grant from the last five minutes. The grant is consumed atomically before changing the password. Successful reset clears the user's custom SMS sessions and requests global Auth sign-out. A stale grant returns the customer to SMS verification.
- Prepared server-authorized Stripe manual capture: exact server order amount, owner-scoped completion endpoint, live price lock, 15-second safety margin, recorded capture authorization, stable provider idempotency keys, and no automatic capture retry on network uncertainty. Expired manual authorizations are released. Bank authorization alone never marks an order paid.
- **Manual capture remains disabled** pending isolated Stripe acceptance tests. Existing automatic-capture payments keep their behavior. The native Auth password-reset gap and late automatic settlement are therefore still launch blockers.
- Added leased reconciliation of bound pending Stripe intents. Jobs retrieve canonical provider state, check order identity/currency/amount, and apply existing guarded payment transitions. Ambiguous attempts without a recorded provider ID are surfaced for manual reconciliation, never blindly released.
- Added Admin → Security → Operations checks: failed/overdue notifications, unresolved card payments, reconciliation failures, sender status, shipping fee and security configuration. Requires server-verified administrator membership and AAL2. This is a pull dashboard, not an outbound alert service.
- Restored the temporary $0 shipping setting to $35, with an audit record. Existing order totals remain unchanged.
- New private ledgers use RLS without client grants; recovery, capture, worker and health RPCs are service-only. No production records were deleted.
- Added completion rate limit of 20 requests per customer per 10 minutes and health-read limit of 30 per admin per 10 minutes. Existing recovery/OTP limits remain in force.

## Validation

`npm run check` passed: product search, 9 signup tests, 71 security/API/database tests, 19 email tests, 13 support tests, and the production build (112 automated tests total). Production dependency audit: zero reported vulnerabilities. Tests include ownership filters, rejected client amounts, missing SMS, normal-user/AAL1 admin denial, forged job tokens, exact capture amount, expired locks, timeouts, one-time recovery grants and reconciliation leases. Provider tests use fixtures, not real Stripe or SMS traffic.

The operations panel is checked with synthetic browser fixtures at desktop and mobile widths, including failure and retry. Existing support, receipt, image and order-action tests remain available. No test charges, refunds, real customer tickets or customer emails were generated by this release.

Production configuration observed: required customer SMS enabled; Resend sender enabled after the owner connected it; shipping $35; no failed/overdue outbox jobs or stuck/unbound card payments at inspection. The outbox had zero accepted customer notifications. Provider acceptance of the connection sample does not establish inbox delivery.

## Recovery procedure

1. Stop affected payment entry points or put the storefront into maintenance when integrity is uncertain; preserve logs and canonical provider IDs. Never remove a card claim just to allow a retry.
2. Reconcile the order with Stripe before fulfilling, cancelling or retrying. Inspect failed notification/reconciliation counts in Operations checks. Preserve audit and payment histories.
3. For application rollback, redeploy the last known-good Vercel deployment. Keep `card_manual_capture_enabled=false` for new intents. Already-created manual intents still require reconciliation; do not remove its endpoint/worker while they exist.
4. If reconciliation needs pausing, deactivate only the named `payment-reconciliation` cron job; preserve its ledgers. Restore it after fixing the cause. Do not reset the database.
5. Before launch, document actual backup retention and recovery targets. Restore a backup to an isolated project with outbound email/SMS/payment jobs disabled. Verify order totals/statuses, items, ownership/RLS, profiles, audit history and storage objects. Never run a restore drill over production.
6. Database backups do not replace a separate backup of product/storage objects or protected configuration. Keep credentials in an approved secret manager. Record restoration evidence and the successful recovery date.
